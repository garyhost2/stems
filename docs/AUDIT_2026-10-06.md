## 2. How a run actually works

### Observations

`stems/environment.py::OBS_NAMES` fixes a canonical 28-element vector, in this order (I printed it
from the source to be sure the hard-coded indices elsewhere are right):

| idx | name | idx | name | idx | name |
|---|---|---|---|---|---|
| 0 | `day_type` | 10–13 | `direct_solar_irradiance` (+3 preds) | 22–23 | `electricity_pricing_predicted_1,2` |
| 1 | `hour` | 14 | `carbon_intensity` | 24 | `cooling_demand` |
| 2 | `outdoor_dry_bulb_temperature` | 15 | `indoor_dry_bulb_temperature` | 25 | `dhw_demand` |
| 3–5 | `..._predicted_1,2,3` (leads 6/12/24 h) | 16 | `non_shiftable_load` | 26 | `occupant_count` |
| 6–9 | `diffuse_solar_irradiance` (+3 preds) | 17 | `solar_generation` | 27 | `..._cooling_set_point` |
|  |  | 18 | `dhw_storage_soc` | 28* | `..._heating_set_point` |
|  |  | 19 | `electrical_storage_soc` | 29* | `heating_electricity_consumption` |
|  |  | 20 | `net_electricity_consumption` | 30+* | EV slots × 5 fields |
|  |  | 21 | `electricity_pricing` |  |  |

\* appended only when `heat_pump=True` / when chargers exist.

Per building, `_obs_indices_per_building` maps canonical name → that building's native CityLearn
index, or `None`; missing entries are zero-filled and a building without a charger gets an inert
padded slot. Heterogeneous buildings therefore present one fixed shape to the network — a good
design, and it is what makes partial EV penetration possible.

Two timing corrections sit on top: `_read_simulated_hour` overwrites the five *endogenous*
observations (indoor temperature, net consumption, both SOCs, heating consumption) with the
simulator's series at the hour the action was applied to; and the exogenous entries are read from
the observation *before* the action by the reward and KPI code. This is CityLearn defect #1 and the
fix is correct as far as I can verify by reading.

### Actions

Canonical order `[dhw_storage, electrical_storage, cooling_or_heating_device, electric_vehicle_storage_0..k]`,
each in [−1, 1], remapped per building to native indices and clipped to the native box. Buildings
without a device simply never receive that column (`_action_slot_to_native`). `hvac_control="setpoint"`
(the default for the house scenarios) does not send the policy action to the heat pump: it is a
±1.5 °C set-point offset, and an integral thermostat (`thermostat_step`, gain 0.05 /°C/h,
0.3 °C deadband) converts the resulting band error into the power command. This is the change that
took discomfort from 66–79% to ~1–5%, and it is the right call.

### Reward

`STEMSReward.compute` returns one scalar per building:

```
r_i = −μ·p_t·max(e_i,0)                                 economic (import only, billed at the hour's own price)
      − α_grid·(Σ_b max(e_b,0) / P_grid_max)²           district grid term — identical for every agent
      − α_build·|e_i| / P_building_max                  own magnitude
      − β_ramp·|e_i − e_i^{t−1}| / P_building_max       own ramp
      − λ_indoor·comfort_i                              squared °C outside [T_heat, T_cool], occupied hours only
      + ξ·min(solar_i/load_i, 1)                        renewable term, ξ = 0 by default
      − ev_service·Σ_departed max(soc_req − soc_left,0) − ev_shaping·shortfall_while_connected
```

with μ=1, α_grid=0.5, α_build=0.3, β_ramp=0.2, λ_indoor=0.4, ev_service=25, ev_shaping=0.5.
The EV departure term reads the simulator's departure record (`env.ev_departures`), not the
observation — correct, because the last connected hour's charge never appears in an observation.

### Constraints

| Constraint | Mechanism | Hard? |
|---|---|---|
| Battery SOC ∈ [0.1, 0.9] | `CBFShield` + `BatteryModel.safe_interval`, bisection on the simulator's own battery step | **Yes** — 0 violations in every stored grid |
| District import ≤ cap (EV + house storage) | `FleetShield` LP over all remaining parking hours + common shed factor on battery/tank charging | **Yes up to forecast error** (3–16 kWh/2 weeks residual) |
| EV SOC at departure | same LP, with a big-M-penalised shortfall variable | **Yes when the set is non-empty**; reports infeasibility otherwise |
| Comfort band | soft term in the reward + a KPI | **No** |
| Per-building power cap | Lagrangian cost + KPI; battery charge trimmed only when `nominal_power` is supplied | Partly |
| Battery / EV degradation | not modelled; cycles counted as a KPI only | **No** |
| Transformer thermal limit, loss of life | not modelled (the cap is a static kW number) | **No** |
| Legionella / DHW service | designed in `docs/dhw_legionella_design.md`, not implemented | **No** |

Plus a PID-Lagrangian on three indicator costs (SOC out of band, |net| > building cap, district
import > grid cap), updated from the episode-mean rate against `cost_limit = 0.05`.

### Training loop

One PPO-Lagrangian update per episode over the whole window (672 steps for 28 days, 336 for 14).
Episode 1 only fits the observation normalizer and takes no gradient step. GAE(λ=0.95, γ=0.99) with
bootstrapping at the window end (correct for time-limit truncation). Reward advantages standardized
per building; cost advantages mean-centred; combined as
`(A − Σ_k λ_k A^c_k)/(1 + Σ_k λ_k)`. 10 epochs × 64-sample minibatches with a 1.5×`target_kl`
early stop. The actor is trained on its **own sampled pre-tanh action**, treating the shield as part
of the environment (Gros et al. 2020) — a defensible and correctly implemented choice. Evaluation is
a separate, freshly built controller loaded from the checkpoint, run with `explore=False` on the
next window; when a fleet shield is present, one pass over the *training* window first warms the
load forecaster, which is causally correct.

## 3. Implemented vs missing

**Implemented and working**: the audited CityLearn wrapper and its three patches; exact battery and
charger/EV-battery plant inverses; exact electric-water-heater tank model; the set-point thermostat;
PPO-Lagrangian with a shared ST encoder; the calibrated SOC barrier; the LP cap shield with causal
forecasting, conformal-style margin, deadline reserve and dead-band handling; eight EV allocation
rules; a KPI suite validated against the simulator's own series; scenario-level statistics with Holm
correction; actuator-response verification; code-fingerprint provenance; 232 tests.

**Missing against the project's own standards**:

- ≥5 seeds (only the untracked `results/ws_paper/` grid has 5; everything in the report has 1–2);
- held-out **buildings** (never done — every run trains and tests on the same houses);
- held-out **weather** (one year, 2018, one location for all thermal results);
- strong baselines (MPC and the six learned comparators exist as code but are unreachable, and as
  written would not survive review — see **A3**);
- a comparison of constrained-RL *methods* (Lagrangian vs CPO vs safety layer vs projection) —
  only Lagrangian and projection exist, and they are not isolated from each other;
- battery/EV degradation as a constraint or cost;
- comfort as a hard constraint;
- any real-data path (the project's stated end goal) — there is no non-CityLearn environment
  adapter, no data-quality audit code, no system-identification module, no offline-RL path;
- sensor noise, missing data, delays, actuator limits, non-stationarity: `set_comm_disruption`,
  `set_temp_offset`, `set_weather_front` exist on the environment and **nothing calls them**;
- any market / mechanism-design object for paper 3 (no agent-level prices, no bids, no allocation
  mechanism beyond the LP; the LP's `cap_shadow_price` is computed and never used).

## 4. Ranked findings

Rank is by *how much of a claim it can invalidate*, not by how hard it is to fix.

### A. Would invalidate a paper claim

**A1 — The only 5-seed grid is trained and evaluated on the same year.**
`results/ws_paper/tx_travis_8b__year-insample__refn8__cap300-80/` (untracked, finished 5 Oct 19:43,
23 runs) uses `season="year"`, and `season_windows("year")` returns `(0, 8759)` for **both** the
training and the evaluation window. I read all 23 records: every one has
`train_window = eval_window = [0, 8759]`. Five seeds for `rl`, `rl+basic`, `rl+linear`,
`rl+calibrated`; one each for `idle`, `rbc`, `rbc+calibrated`. Costs 17,670–23,399; `rl+calibrated`
reports 0.0000 safety violations on all five seeds.

The scenario key says `year-insample`, so the code is honest with itself. But this is the grid that
matches the STEMS paper's protocol (full year, five seeds), it is the only grid that meets your
≥5-seed standard, and it is therefore the one most likely to end up in the WSED table. **Nothing
from it can be reported as out-of-sample performance.** Fix before use: split the year
(train `[0, 4379]` / test `[4380, 8759]`), or train on 2018 and test on another ResStock weather
year, or leave-one-season-out with the seasons pooled.

**A2 — No held-out buildings, anywhere.**
`Scenario.subset_seed` draws a different set of 8 houses from the 39 with the reference device set,
but each run then trains *and* evaluates on its own set. There is no run in this repository that
evaluates a policy on a building it never saw. Generalisation across buildings is the claim a
reviewer will test hardest for a "neighbourhood" controller, and there is currently zero evidence
for it. Same for weather: one year, one county, for every thermal result.

**A3 — The baseline suite is unreachable, and would not survive review if switched on.**
`ARMS` contains only `idle`, `rbc` variants, `hp-shift`, and six variants of the same
PPO-Lagrangian. `SingleAgentSAC`, `DMAPPOAgent`, `MPCAgent`, `MADDPGAgent`, `MARLISAAgent`,
`MADCQAgent`, `MetaEMSAgent` are exported from `stems/__init__.py`, exercised by no experiment, and
instantiated by no code path I could find. So the honest statement today is: *the method is compared
against doing nothing and against one hand-written rule.* The report says this; the README's results
table does not make it equally obvious.

Switching them on as they stand would be worse than leaving them off:

- `MPCAgent`: 6-step horizon, battery only, **price held constant over the horizon**, SOC dynamics
  `soc + 0.1·Σu` with a hardcoded η = 0.1, no load or PV forecast, no comfort, no cap, falls back to
  a two-threshold heuristic when cvxpy is absent. This is not a model-predictive controller; beating
  it proves nothing.
- `DMAPPOAgent`: one-step TD advantage (no GAE), optimizer step inside the epoch loop against a
  fixed `old_log_prob`, no value clipping, no entropy term, and a "CBF penalty" subtracted from the
  stored rewards using the same hardcoded 0.1 SOC rate.
- `MADCQAgent`: 11³ = 1331 discrete actions, fixed ε = 0.1, no replay buffer (it learns from the
  on-policy episode), SOC clamp again on the hardcoded rate.
- `MARLISAAgent` augments building *i*'s observation with buildings `0..i−1`'s actions from the
  **same** time step during action selection but with the *stored* actions during update — the
  sequential decision structure is not reproduced in the update.
- `MetaEMSAgent` is `SingleAgentSAC` with a 50/50 parameter average after two updates on halves of
  the batch; it is not MAML or Reptile in any recognisable sense.

Recommendation: delete them from `__init__`, and re-implement MPC and one learned baseline properly
(or wrap an external implementation) rather than resurrecting these.

**A4 — Seed count and the unit of replication.**
Everything in `docs/REPORT_2026-10.md` is 1–2 seeds. The decision to treat a *scenario* as the
replication unit and average seeds inside it is correct and well implemented (`aggregate.py`
pairs learning arms on matched seeds only, applies Holm across three pre-declared KPIs). But with
n = 8 scenarios and 2 seeds, the cost CIs in §5 span ±300 on a mean of ~1,550 — the study is
powered to detect the barrier's effect on violations and essentially nothing about cost. Any
sentence of the form "learning is cheaper" needs either many more scenarios or a much larger effect.

**A5 — The known reward-hacking case is real and the fix changes the environment between arms.**
REPORT §6.7 documents it honestly: behind the deadline shield the plain learner requests 0.2–3% of
the cars' energy and lets the shield charge at the joint last feasible moment, which is cheap, and
pays for it with 14/9 missed departures of 67. The chosen remedy (tighter shield margins, §6.8)
modifies the *shield* — i.e. the environment — so any table mixing §6.7 and §6.8 numbers compares
policies under two different dynamics. §6.8 does re-run the rules, which is the right thing; keep
that discipline and label the shield version in every EV table.

### B. Correctness bugs

**B1 — `CBFShield._apply_hvac_power_guard` rescales by the wrong factor.** `stems/cbf.py`:

```python
total = float(np.maximum(net + np.abs(safe[:, self.hvac_idx]) * p_nom, 0.0).sum())
if total > g_cap and total > 1e-6:
    safe[:, self.hvac_idx] *= g_cap / total
```

Scaling the *action* by `cap/total` does not bring the total to the cap, because the uncontrollable
`net` term is scaled too. This is exactly the arithmetic error REPORT §6.7 says was found and
corrected in the battery grid guard — the corrected version there bisects on the achieved import.
The HVAC guard still has the original form. It is currently inert because `cop_model` is never
passed by `build_controller` (so the guard returns at its first line), but it is live, wrong code
one keyword argument away from being used.

**B2 — `CBFShield.predicted_constraint_costs` uses the linear battery** (`next_soc = soc + a·rate`)
even when an exact `BatteryModel` is attached, contradicting the rest of the shield. Dead today
(never called), but it is the natural place a future cost-critic target would be wired in.

**B3 — Reward and cost advantages are on incompatible scales in the Lagrangian.** In
`STEMSAgent.update`:

```python
adv  = (adv - adv.mean(0)) / (adv.std(0) + 1e-8)      # standardized
cadv =  cadv - cadv.mean(0)                            # mean-centred only
eff_adv = (adv - (cadv * lam_k).sum(-1)) / (1.0 + lam_k.sum())
```

λ therefore has no stable meaning: its effective weight depends on the raw spread of the cost
advantage, which with 0/1 indicator costs and γ = 0.99 is O(10) while `adv` is O(1). A λ tuned on
one scenario will not transfer to another, and the λ traces logged per episode are not comparable
across runs. Standardize `cadv` the same way (or normalise by its own running std).

**B4 — Every agent's reward contains the identical district grid term.** With independent actors and
independent critics and no centralised critic, the global penalty is pure noise in each agent's
credit assignment. This is the most likely mechanical explanation for the result you already have —
the learner fails to find battery arbitrage in winter (4–5 cycles against the rule's 13) while
finding it in summer when the PV signal is strong enough to dominate. Worth testing directly with a
difference-reward or a centralised critic before concluding anything about "learning vs rules".

**B5 — Two incompatible definitions of district import inside `MetricsCalculator`.**
`avg_daily_peak` and `ramping_rate` use the **signed** sum `net.sum(axis=1)` (one building's export
offsets another's import); `peak_import_kw`, `cap_exceedance_kwh` and `grid_violation_rate` use the
**positive-part** sum `Σ_b max(net_b, 0)`. The shield, the CBF and the reward all enforce the
positive-part definition, and `tests/test_kpis.py::test_exports_do_not_offset_another_buildings_import_for_peak`
pins it for the peak — but not for `avg_daily_peak`. So the headline "average daily peak" is not the
quantity any constraint in this repo controls.

**B6 — The building graph's spatial term is fabricated and carries no information.**
I checked the vendored CityLearn 2.6.0b1 source: `Building` exposes no `latitude`, `longitude` or
`floor_area`. `STEMSEnvironment.get_building_info()` therefore always takes its fallbacks:
coordinates `(30.26 + 0.01·i, −97.74 + 0.01·i)` generated from the **building's index in the schema**,
and a constant floor area of 150 m². With σ_d = 1.0, the positional half of every edge weight lies in
**[0.497556, 0.500000]** — a spread of 2.4 × 10⁻³ across all 56 off-diagonal edges. The floor-area
feature is identical for all buildings and contributes nothing. The only varying input to the
adjacency is the min–max-normalised battery capacity.

The "spatial" half of the spatio-temporal encoder is therefore a near-uniform mean-pool over
buildings whose one real input is battery size, and the distance term is a function of schema
ordering. For a paper whose architecture claim is "spatial-temporal enhanced", this needs either
real coordinates and areas (ResStock metadata has them) with σ_d re-tuned to the actual spacing, or
an explicit statement that the graph is feature-based and a corresponding ablation against a plain
mean-pool.

**B7 — `HistoryBuffer` is zero-filled at every reset,** so the transformer's first 23 steps attend
over a window that is mostly the *normalised value of zero*, not a missing-data token. On 14-day
episodes that is 7% of every episode and it is the part where the policy also has the least
normaliser calibration.

**B8 — The observation list is duplicated and the two copies disagree.**
`setup_citylearn_8b.py::STEMS_OBSERVATIONS` force-activates 27 observations but omits
`dhw_storage_soc`, `indoor_dry_bulb_temperature_heating_set_point` and
`heating_electricity_consumption` — all three of which `stems/environment.py` requires (index 18 and
the two heat-pump entries). The generated schema works only because those are already active in the
upstream Travis schema. If upstream changes, the environment either raises or, with
`--allow-missing-obs`, silently zero-fills the DHW SOC that the tank model, the shield and the KPIs
read. One list should generate both.

**B9 — Hard-coded observation indices in eight places.** `_IDX_SOC_ELEC = 19`, `_IDX_NET = 20`,
`_IDX_T_IN = 15`, `_IDX_T_SET = 27`, `tank_soc = 18`, `tank_demand = 25`, `load_index = 16`,
`solar_index = 17`, `net_index = 20` appear independently in `cbf.py`, `reward.py`, `metrics.py`,
`baselines.py`, `fleet.py`, `thermal.py`, `runner.py` and the diagnostics. I verified all of them
against `OBS_NAMES` and they are currently correct. There is no assertion anywhere binding them to
the names, so one insertion into `OBS_NAMES` silently corrupts the reward, the shield and the KPIs
simultaneously, with no test failure that points at the cause. `STEMSEnvironment` should own
`index_of(name)` and everything else should ask it (or at minimum a module-level
`assert OBS_NAMES[19] == "electrical_storage_soc"`-style guard).

### C. Constraint handling — the core of the thesis

**C1 — Two hard constraints, not five.** As tabulated in §2: the SOC band and the district cap are
genuinely enforced; the EV departure SOC is enforced when feasible and reported when not (which is
the correct design and should be stated that way); comfort is soft; per-building power is
Lagrangian-only; degradation and transformer limits do not exist. Your brief says comfort and
equipment limits should be hard unless told otherwise — right now comfort is a quadratic penalty
with weight 0.4 and nothing else. That is a gap between the stated position and the code.

**C2 — The Lagrangian is vestigial in the arms you actually run.** In `rl+calibrated`, the exact
barrier drives the SOC cost to ~0, so λ decays and the Lagrangian contributes nothing; in `rl`,
there is no barrier so the Lagrangian is the whole story (9.1% violations). There is no arm that
holds the budget fixed and varies *only* the constraint mechanism. The clean 2×2 — {no mechanism,
Lagrangian, projection, both} — is the natural ablation for a constrained-RL paper and it is one
line in `ARMS` plus a grid run.

**C3 — No CPO, no comparison of constrained-RL families.** The brief asks for Lagrangian vs CPO vs
safety layers/shielding vs action projection, compared on violation rate. Present: PID-Lagrangian
(one variant) and two projection shields. `NeuralSafetyFilter` — a learned projection, which would be
the fourth family — is written, has a loss function, and is never trained or called.

### D. The MARL claim

**D1 — There is no multi-agent algorithm in the live path.** With `share_parameters=True` (the
default — `ablation.py` passes `not args.per_building_actors`), `STEMSAgent` holds **one** actor,
**one** critic and **one** cost critic, applied to each building's encoded state. The only coupling
is the single GCN layer stack mixing observations, plus the shared district reward term. That is
parameter-shared independent PPO on a graph-encoded observation. It is not MAPPO (no centralised
critic), not CTDE, not MADDPG, and there is no communication protocol. Calling it MARL in a paper
invites a reviewer to ask which multi-agent mechanism is being evaluated, and the answer today is
"none beyond parameter sharing and a graph encoder".

**D2 — The coordination result you have is a scheduling result, not a MARL result.** The EV finding
— per-vehicle latest-start fails when charging is deferred because each car's deadline is
individually reachable and the set is not; the joint LP recovers it (248 kWh → 31 kWh at 40 kW) —
is, in my reading, the strongest and most defensible contribution in the repository. But it is
produced by a **centralised optimiser**, not by learned multi-agent coordination. Frame it as such.
It also sets up paper 3 well: the LP's dual on the cap constraint (`cap_shadow_price`, already
computed and currently discarded) is exactly the price signal a market formulation needs.

### E. Reproducibility and provenance

**E1 — The code fingerprint does not cover the experiment.** `code_fingerprint()` hashes
`stems/*.py` and `experiments/*.py`. It does **not** cover the schema JSONs (gitignored, regenerated
per machine), the EV charger CSVs or the `--ev-buildings`/`--seed` that produced them, the CityLearn
source (only `__version__` is recorded), or `requirements.lock.txt`. Two records with the same
fingerprint can be different experiments. Hash the resolved schema file, the charger CSVs and the
CityLearn version into the record.

**E2 — The charger CSV "modification" is a line-ending artefact.** All six tracked
`citylearn_schemas/tx_travis_8b_ev/charger_*.csv` show as modified. I verified they are
byte-identical to `HEAD` after stripping `\r` (md5 `1c6a1eb6467d7ca44568fb9a644db9e7` both ways) —
a CRLF/LF drift, not a data change. `.gitattributes` currently contains only `*.sh text eol=lf`.
Adding `*.csv text eol=lf` removes the false drift, and removes the paragraph in REPORT §9 that has
to explain why the committed tree hashes differently from the grid's copy.

**E3 — `seed` never reaches CityLearn.** `STEMSEnvironment.__init__` stores `self._seed` and uses it
only for the mock; the real `CityLearnEnv` is constructed without `random_seed`. Harmless today
because the simulation is deterministic given the schema, but it means "seed" seeds only
torch/numpy/python, and a future stochastic element (or a stochastic EV schedule) would be
unreproducible. It also silently explains why non-learning arms are run with a single seed.

**E4 — The newest results are outside version control.** `results/ws_paper/` (23 records plus 20
model directories) and `train.out` are untracked; `results/**/*_model/` is gitignored, so no saved
policy in the repository can be replayed. `experiments/diagnostics/ev_rl_requests.py` and
`replay_saved_policy.py` both need those checkpoints and will fail for anyone cloning the repo.

### F. Smaller items

- `RuleBasedAgent.CHARGE_HOURS = range(11,17)` / `PEAK_HOURS = range(17,22)` are hardcoded to the
